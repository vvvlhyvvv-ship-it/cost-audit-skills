# 结算书明细 → 合并汇总：更新与差异溯源

> 固化某县高标准农田项目（15 村、约 559 行结算书 / 70 行合并汇总）反复迭代中踩过的全部坑。
> 该任务已重复 8+ 轮：**用户每次调整 Sheet2 后要求"更新合并汇总"**，并常伴随"数字不对"的差异质疑。

> 与 `selftest_gap_report.py`（**反向构造缺陷**自测，已实测 5/5 通过）。定位缺陷改用

## 0. 两类文件与列语义（先确认，勿凭记忆）

**源 = 结算书（如 `工程结算书8-28 - 副本.xlsx`）**
| 列 | 含义 |
|---|---|
| col1 序号 | 层级：`一/二…/十五`=村；`（一）（二）`=工程类别；`1`/`1.1`/`1.1.1`=子目 |
| col2 单项名称 | **父类别解析只看 col2**（序号在 col1） |
| col3 单位 | 可能有单元格内换行（如 `1000m\n2`） |
| col4 报送工程量 / col5 审定工程量 | — |
| col6 综合单价 | **有值 = 叶子行（定额行）**；空 = 表头 |
| col7 报送合计 / col8 审定合计 | 金额来源，**只搬这两列** |

**目标 = 合并汇总表（如 `工程结算书合并汇总.xlsx`）**
| 列 | 含义 |
|---|---|
| col4 报送工程量 / col5 审核工程量 / col6 综合单价 / col7 报送金额 / col8 审核金额 / col9 审核−报送 | 需更新 |
| col10 J / col11 K | **复核列公式** `=E*F`、`=H-J`（不要动，也不要指望它等于 0） |
| r102 | 合计行（名称含"计"） |
| r103 col8 | **对账基准 = 结算书审定合计**（常量，用户维护） |
| r104 col8 | **`=H102-H103` → 必须归零**（用户加的对账检查） |

## 1. 匹配与取数（核心规则）

1. **主键 = (父类别名, 定额名, 单位, 单价)**，四元组缺一不可。
   - ❌ 只用 (定额名, 单位, 单价) 会把同一定额在不同父类别下（底土平整/客土回填/表土剥离 下的"推土机"）跨类合并，金额翻倍（本项目曾算成 1.22 亿）。
2. **父类别 = 最近一个表头的 col2 名称**（用序号层级 `level_of` + 栈维护；`（`开头=0 层，`X.X`按点数+1）。
3. 名称规范化 `nq()` = 去空白 + **先跑别名再剥后缀** + 截断长名。
   - 别名：`装石碴自卸汽车运输→石碴运输`、`挖掘机装石碴→石碴`、`挖掘机挖装运土→挖装自卸汽车运土`、`伸缩缝→道路伸缩缝`
   - 后缀：载重量、推土机功率、`1m³挖掘机`、运距、`推土距离.*`、厚度、三类土、机械夯填、其他机械、φ…mm、`（51m）`、机械摊铺(压实)、压实、沥青木板、`[...]`、`（…：…）`
   - 长名截断：`re.sub(r"(C25混凝土渠).*", r"\1", n)`
4. **单位规范化 `nu()`**：去换行 → `m3→m³`、`m2→m²`、`hm2→hm²`、`km2→km²`（源表用 ASCII，目标表用上标）。
5. **合并名**：目标表含 `/` 的名称（如 `道路切缝/伸缩缝`）按 `/` 拆开各分部求和，命中即算匹配。
6. **金额列（col7/col8）直接搬源表原值，工程量列（col4/col5）必须保留源表完整精度。**
   - 🔴 **工程量绝对不要 `round(x, 3)`**。源表存在 `0.0125`、`8.34652705061082`、`0.832670157068063`、`16.8802094240838`、`25.4162652705061` 这类高精度工程量；截断到 3 位后 × 单价会产生**几十元级**的金额偏差（本项目 r58 C25砼预制板：`0.0925→0.092`，差 **40.01 元**；共 10 行受影响、Σ差 2.72 元）。
   - 正确写法：用 `Decimal` 聚合求和后 `float(round(v, 10))` 去掉浮点尾数即可，10 位足够。
   - 验证标准：**`工程量 × 单价` 必须等于该行金额**（源表 col8 本身就是 `col5 × col6` 精确结果）。
   - ⚠️ 教训来源：曾把根因误判为"不能用工程量×单价反推金额"，于是只搬金额、把工程量 round 到 3 位，结果表内换算列 `J=E*F` 与 `H` 对不上（10 行，最大 40 元）。**真正的错因是截断了工程量，不是反推。**
7. **两列的精度天生不同，别试图让它们都对齐**：
   - 源表 **报送金额 col7 最多 2 位小数**（本身就是"取整到分"）→ 目标 `D×F` 与 `G` 必然有 ≤0.03 元的分位级差异，**属源表特征，不要处理**。
   - 源表 **审定金额 col8 保留 3~10 位完整精度** → 目标 `E×F` 与 `H` **应当完全一致**（这是可校验的硬指标）。
8. **固定置零行**（本项目）：r18 推土机单价 201.15（后子坪村异常价，应按 248.94）、r44 素土路肩 3411.94（源表无此单价）。置零前必须核实"源表确无对应项"。
9. **存储精度**：叶子行金额按源值存 **6 位小数**（`round(v,6)`）。作用：去掉浮点尾数（如 `5308013.210000001`），同时保证 **Σ行 = 合计 = r103 精确相等**。显示格式 `#,##0.00` 不受影响（仍两位小数）。
10. **表头行的 亩/㎡ 面积量不做 roll-up**（单位与叶子不同），保留原值。

## 2. 落盘后必须做的**四项**校验

```
① Σ(叶子行 col8) == 合计行 col8 == r103 col8      → 残差必须 0
② 源未被消费的聚合项 == 0 项（无重复计、无遗漏）
③ 叶子匹配率：本项目 68/70（另 2 行是固定置零行）
④ 【必做，曾被漏掉】逐行校验 col5 × col6 == col8  → 差异 ≥0.005 元的行数必须为 0
   （用 Decimal 算，不要用 float；col5 若被 round 过，这里会立刻暴露）
```

- 🔴 **③ 通过 ≠ 表是对的**。合计数对得上，但单行 `工程量×单价 ≠ 金额` 说明取数环节被截断过。
  本项目就出现过"合计完全正确、但 10 行 J 列对不上（最大 40 元）"的情况，是靠④才发现的。
- `r104 = H102-H103` 是公式；用 openpyxl 存盘会清掉公式缓存，**须提示用户用 WPS/Excel 打开一次触发重算**（同理会重算 J/K 复核列）。
- 打开时若公式列显示空或旧值，让用户按一次 F9。
- openpyxl 存盘后 `data_only` 读 J/K 会得到 `None` —— 这是缓存被清，**不是**公式错误；不要据此判定"J 列不符"（会误报几十行）。要校验就用④的算术方式。

## 3. 「数字不对 / 审定的合计是 X」怎么查（公式链溯源）

**现象**：用户报的审定合计（源表项目级 r4）与明细叶子求和不一致。

**步骤**：
1. 算两个口径：`∑(叶子行 col8)` vs 源表 `r4`（项目级）。差额往往**恰好等于某个新增子目的金额**。
2. 用 `scripts/formula_chain_audit.py` 沿公式链从 r4 展开，求"未被覆盖的叶子行"。
   - ⚠️ **必须支持区域引用 `H48:H52`**：只取端点行会误报大量"未覆盖叶子"（本项目曾误报 101 行）。正确的实现见脚本文末的 `expand_refs`。
3. 同时跑"全表一致性审计"：逐行比对 `父行值 vs 其公式引用子行之和`，一次性找出所有公式缺陷（本项目结果：除核减额派生行 `=H4-H558` 外，仅 r238 一处不一致）。
4. **判定"漏改公式"还是"有意不计"**（决定 6 位数金额的去向，必须让用户拍板）：
   - 报送列公式已含新增行、审定列漏 → 典型的"同处插入只改一列"
   - 该项明细审定值非 0、非空
   - 该表"不予认可"的**既有写法是把审定工程量置 0**（去找这类行作旁证）
   - 同为新增的其它子目已被父行公式引用
   → 以上皆成立则倾向"漏改公式"；反之若作者一贯用置 0 表达不认可、且新增行是自己粘贴的，则可能是有意不计。
5. 把两种口径的**核减额**摆给用户（本项目差 63,786.54 → 核减额 954,773.67 还是 890,987.14），用 `AskUserQuestion` 让其一句定夺，**不要自行拍板**。

## 4. 修父行公式：外科式改 XML，不要用 openpyxl

源表 col7/col8 全是公式。**用 openpyxl 存盘会清掉全表公式缓存**，导致后续脚本 `data_only` 读不到值。

正确做法（`scripts/patch_parent_formula.py`）：
1. 确认源表**只有一个 sheet、无 `xl/calcChain.xml`**，且 `<calcPr>` **没有 `fullCalcOnLoad`** → 必须自己同步父行缓存值，否则 Excel 打开显示旧值。
2. `zipfile` 读出 `xl/worksheets/sheetN.xml`，正则替换目标单元格：
   `<c r="H238" s="26"><f>SUM(...)</f><v>旧值</v></c>` → 新公式 + 新缓存值
3. 原样重写 zip（其余条目与全部缓存字节级保留）。
4. **必须连带更新所有受影响祖先的缓存值**：先扫出所有引用该单元格的公式（`re.search(r'(?<![A-Z0-9])H4(?![0-9])', 公式)`），逐个算新值。
   - 例：H238 修正 → H213、H4、核减额行 `=H4-H558` 三处缓存都要同步。

**写盘前先跑可写性探测**：
```python
try:
    open(path, "r+b")
except PermissionError:
    # 文件正被 WPS/Excel 打开（同时会存在 ~$xxx.xlsx 锁文件）
```

**被占用时不要卡住 —— 用「副本落盘」双分支**（`scripts/patch_parent_formula.py` 已实现）：
```python
if writable(SRC):
    TARGET = SRC                       # 原地修正
else:
    TARGET = SRC.replace(".xlsx", "_已修H238公式.xlsx")   # 副本修正，原文不动
    # 注意：zip 内容始终从 SRC 读（只读不阻塞），只把落盘目标换成副本
```
- 这样用户**始终能立刻拿到修正结果**，不必等关闭 WPS；关闭后重跑同一脚本会自动改为原地修正（幂等：已修过输出 `ALREADY`）。
- 副本命名要带**改了什么**（`_已修H238公式`）而非日期，用户一眼知道差异。
- ⚠️ 锁文件 `~$xxx.xlsx` 存在 ≠ 一定写不进去，也**不要删锁文件**（删了不解除句柄，还会破坏对方编辑态）；以 `open(r+b)` 探测为准。
- 定位占用进程：`tasklist /FI "IMAGENAME eq wps.exe"`（注意 subprocess 读取要用 `errors="replace"` 或 `encoding="gbk"`，否则中文输出会抛 `UnicodeDecodeError`）。

## 5. 差异核查报告（一条命令自动生成）

把第 3 节的五步溯源做成脚本，**换项目只需改 `SRC`/`DST`/`REPORT` 三个路径**：

```bash
python scripts/gap_report.py      # 产出 3 张 sheet 的 xlsx + 一份 .txt 日志
```

**报告结构**（自动填充，无需手写）：
| sheet | 内容 |
|---|---|
| `差异溯源` | 16 条：两级口径对比 → 差异 → 漏覆盖行 → 缺陷定位 → 证据②③④ → 目标表印证 → 两口径裁决 |
| `差异明细` | 每个漏覆盖叶子行的行号/父类别/定额名/单位/单价/报送量/审定量/报送额/审定额 + 合计 |
| `两口径对照` | A 不计入 vs B 计入 → 报送合计/审定合计/核减额/落盘做法，供用户直接圈选 |

**日志会打印的关键诊断块**：
```
【口径对比】  ① 明细口径 Σ(叶子 col8)  ② 合计口径 r4 col8   差异 ①−②
【公式链展开】H 列链覆盖/漏  G 列链覆盖/漏
              ├ ★H 漏、G 有（只改了报送列的铁证）: N 行 [行号...]
【缺陷定位】  G/H 公式链分叉点：r238
              r238 G = =SUM(G239,...,G294)
              r238 H = =SUM(H239,...,H286)
              → G 列引用了 ['r294']，H 列没有  ← 缺陷就在这个汇总行
【旁证】      该表『不予认可』= 审定工程量置 0 的行：3 行 ['r266','r268','r275']
              而漏覆盖的 6 行中，有 6 行是『审定量 = 报送量』（并非置 0）
```

### 🔑 缺陷定位的关键：找「分叉点」，不是找「父行」

**别用"引用目标行的最小行号"**。漏覆盖行 r296 的最小引用行是 r295（项8 内部 `=SUM(H296:H301)`），
而 r295 的 G/H 公式是**对称的**（都含 296:301），不构成任何证据。真正的漏引发生在更上层的汇总行 **r238**。

正确做法：从项目级合计行出发，沿 **G 列与 H 列的公式链同时向下**，返回**第一个两边引用集合不一致的行**：
```python
def find_divergence(start_row, col_g=7, col_h=8):
    stack, seen = [start_row], set()
    while stack:
        r = stack.pop()
        if r in seen: continue
        seen.add(r)
        sg = {rr for rr, cs in refs_in(sf.cell(r, col_g).value).items() if col_g in cs}
        sh = {rr for rr, cs in refs_in(sf.cell(r, col_h).value).items() if col_h in cs}
        if sg != sh: return r, sorted(sg - sh), sorted(sh - sg)   # 分叉点 = 缺陷处
        stack.extend(sorted(sg))
    return None, [], []
```
→ 对某县表返回 `r238`，且 `sg - sh = {294}`，正好指出"G 引用了 r294、H 没引用"。

### 自测（改了脚本后必跑）

```bash
python scripts/selftest_gap_report.py
```
原理：**反向构造一处已知缺陷** —— 在源表审定列找一个"引用集合全为叶子行"的公式行，
用外科式 XML 把它重写成"显式列表、去掉最后一项"，同步把项目级合计行缓存减去该行金额，
然后跑 `gap_report.py` 并断言：差异 == 被删行金额、漏覆盖 == {被删行}、缺陷定位 == 被改行。
*实测结果：自动选中 r50（`=SUM(H51:H57)`）漏掉 r57（12,365.2368 元），5 项断言全过 —— 证明脚本通用，不依赖项8 特定情形。*

> ⚠️ 写这种自测时，`re.sub` 的**替换串里含 Windows 路径会被当成转义序列**（`\W` → `bad escape`）。
> 必须用 `re.sub(pat, lambda m: repl, s)` 形式。

## 6. 其它工程纪律

- **必先备份**：源表与目标表各复制一份带时间戳/说明的备份（如 `_备份20260914_修H238前.xlsx`）。**重跑脚本时要防止把"已修改的文件"覆盖掉原备份** —— 备份语句加 `if not os.path.exists(bak)` 只跑一次。
- 每次改完写项目记忆：差异来源、口径裁决、受影响单元格、备份文件名。
- 用户是造价工程师，**口径（是否认可某新增子目）永远由他定**，AI 只负责把证据链和两种口径的金额后果摆清楚。
- Bash 工具偶发 PATH 丢失 → 改用 PowerShell，或把脚本输出写进 `.txt` 再用 Read 读取。
- **生成/更新 Excel 报告要幂等**：写完一次后重跑会撞上自己建的合并单元格 —— `MergedCell.value` 是只读的，会抛
  `AttributeError: 'MergedCell' object attribute 'value' is read-only`。清理函数必须先解除合并：
  ```python
  def norm(ws, start_row):
      for mc in list(ws.merged_cells.ranges):
          if mc.min_row >= start_row: ws.unmerge_cells(mc.coord)
      for r in range(start_row, ws.max_row + 1):
          for c in range(1, ws.max_column + 1): ws.cell(r, c).value = None
  ```
- **技能脚本的语法自检不要用 bash 的 `~` 路径**（`for f in ~/...` 拼出的路径 Python 收不到）：
  直接用 Python 内部 `os.listdir(SK)` + `py_compile.compile(p, doraise=True)`。
- 交付时**主动交代"哪些差异是源表特征、不是错误"**（如报送额 2 位取整），否则用户会继续追问。

| `selftest_gap_report.py` | `gap_report.py` 的**反向构造自测**（实测 5/5 通过）；改过脚本后必跑 |
| `formula_chain_audit.py` | 只做公式链展开 + 全表一致性审计（`gap_report.py` 的轻量版，用于排查） |
| `patch_parent_formula.py` | 外科式修源表汇总行公式并同步祖先缓存值（**被占用则自动落副本**、幂等） |
| `clean_precision.py` | 叶子行金额 6 位小数清理，保证 Σ行=合计=r103 |

脚本顶部都有「配置区」，改 `BASE`/`SRC`/`DST`/`REPORT` 路径常量即可复用。推荐执行顺序：

```
【常规更新】
  merge_update.py → clean_precision.py → verify_after_merge.py
                                        └─ 若第④项校验不过：qty_precision_fix.py → 再 verify

【用户报「数字不对 / 审定的合计是 X」】
  gap_report.py                        ← 一条命令出报告：差异/来源/证据/两口径
    └─ 用户裁决口径后：
         · 口径 B（计入）：patch_parent_formula.py 修源表汇总行公式 → verify_after_merge.py
         · 口径 A（不计入）：改目标表相应行 → 重设 r103 → verify_after_merge.py

【改过技能脚本后】
  selftest_gap_report.py               ← 反向构造缺陷，确认脚本没被改坏
```
